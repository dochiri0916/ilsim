# 일심 작업 절차

1. 요청이 코드·문서 변경이면 `start_task`에 사용자 요청 원문을 넘긴다. 질문·설명 요청이면 작업을 만들지 않고 답만 한다.
2. 돌려받은 단계 지시대로 허용된 경로만 고친다. 진행 중인 작업이 있으면 `next_step`으로 현재 지시를 받는다.
3. 작업 중간에 `check_change`로 허용 경로·아키텍처·컨벤션·위험·테스트 무결성을 미리 볼 수 있고, `get_rules`로 지켜야 할 규칙을 본다. 단계 지시의 "프로젝트 문서 지침"은 반드시 지킨다(제출 때 일심이 준수 여부를 판정한다). 지침이 불합리해 보여도 임의로 건너뛰거나 바꾸지 않고 적힌 그대로 따르며, 지침끼리 또는 요구사항과 충돌해 따를 수 없으면 멈추고 사용자에게 묻는다. 다시 볼 때는 `get_guidelines`를 쓴다. 단계를 마치면 `submit_result`를 호출한다. 실패하면 지적된 부분만 고치고 다시 제출한다.
4. 요구사항·테스트 케이스 단계는 사용자 승인이 있어야 다음으로 간다. 산출물을 요약해 보여 주고 승인 여부를 묻는다. 사용자가 승인한다고 말하면 `approve_stage`, 고칠 점을 말하면 `reject_stage`(사유)를 호출한다. 사용자가 답하기 전에는 호출하지 않는다. 호출하면 앱이 사용자에게 다시 확인받는다. 일심이 준수를 확인하지 못한 지침이 있다고 알려 주면 승인을 묻기 전에 그 지침과 출처를 사용자에게 알린다.
5. 작업 중에는 git commit·push·병합·브랜치 변경을 하지 않는다. 커밋은 일심이 단계를 통과할 때 한다(직접 커밋은 pre-commit 훅이 막는다). 작업이 끝난 뒤 사용자가 요청하면 작업 브랜치 병합·푸시는 할 수 있다.
6. 작업이 차단되면 사유를 알리고, 사용자가 다시 하자고 하면 `retry_task`(사용자 지시)를 호출한다. 규칙을 새로 뽑아야 하면 `analyze_project`를 쓰고(코드 관행과 함께 문서에 적힌 규칙 중 기계적으로 확인되는 것은 정적 규칙 `doc:`으로 옮긴다), 사용자가 규칙을 검토할 때는 `review_rules`로 보여 준 뒤 사용자가 정한 대로 `decide_rules`를 호출한다.
7. 앞 단계 산출물(예: 테스트 기대값)이 틀려 지금 단계를 통과할 수 없으면 제출해 시도를 낭비하거나 지금 단계에서 우회하지 말고, 사용자에게 사유를 알린다. 사용자가 되돌리자고 하면 `reopen_stage`(단계 `TEST_CODE`, 고칠 점)를 호출한다. 지금 단계의 미커밋 변경은 일심이 보관했다가 그 단계로 돌아오면 되살린다.
8. 사용자에게 보고할 때 단계 결과와 검증 결과를 함께 알린다.
