# 테스트 컨벤션

아래 규칙은 단위 테스트와 통합 테스트를 작성할 때 적용한다.

- 단위 테스트는 클래식 테스트 기법을 기본으로 한다. 테스트 대상의 상태와 반환 결과를 중심으로 기대 동작을 검증한다.
- 도메인 객체와 단순 협력 객체는 가능한 실제 객체를 사용한다. 외부 시스템·DB·메시지 브로커 등 단위 테스트 범위를 벗어나는 의존성에는 Mock 또는 Fake를 사용할 수 있다.
- Mock을 이용한 런던 테스트 기법은 상호작용 자체를 검증해야 하는 경우에 제한적으로 사용한다. 외부 API 호출 여부, 메시지 발행 여부, Repository 호출 여부 등이 이에 해당한다.
- 상호작용 검증은 테스트의 의도와 관련된 호출과 인자를 중심으로 작성한다. 요구사항과 무관한 내부 호출 순서나 횟수를 검증하지 않는다.
- 통합 테스트는 실제 컴포넌트 간의 연결과 동작을 검증한다. 통합 대상에는 가능한 실제 구현체를 사용하고 불필요한 Mock 사용을 지양한다.
- DB 통합이 필요한 테스트는 실제 테스트 DB 또는 Testcontainers 등을 사용해 저장·조회·제약 조건 등 실제 DB 동작을 검증한다. 통합 대상인 Repository나 DB를 Mock으로 대체하지 않는다.
- 각 테스트는 실행 순서에 의존하지 않는다. 공유 상태와 DB 데이터는 테스트마다 초기화하거나 격리해 다른 테스트의 결과에 영향을 주지 않도록 한다.
- 현재 시각·난수·비동기 처리에 따라 테스트 결과가 달라지지 않도록 한다. 필요하면 고정된 `Clock`과 명시적인 입력값을 사용하고, 비동기 처리는 임의의 대기 시간 대신 완료 조건을 기준으로 검증한다.
- 정상 흐름뿐 아니라 업무 규칙 위반과 경계값을 검증한다. 예외 테스트는 구체적인 예외 타입을 확인하고, 오류 메시지나 코드는 계약에 포함된 경우 검증한다.
- 테스트 코드는 `// given`, `// when`, `// then` 순서로 작성한다. `given`에는 테스트 데이터와 사전 조건, `when`에는 검증할 동작, `then`에는 상태·반환 결과 또는 필요한 상호작용 검증을 둔다.
- `@DisplayName`에는 테스트의 의도와 기대 결과를 한국어로 명확하게 작성한다. 예: `@DisplayName("재고가 부족하면 주문을 거절한다")`.
- 테스트 메서드 이름은 `snake_case`로 작성하고 테스트 조건과 기대 결과를 드러낸다. 예: `rejects_order_when_stock_is_insufficient`.

테스트 대상의 업무 규칙과 책임은 [도메인](domain-conventions.md), [애플리케이션](application-conventions.md), [어댑터](adapter-conventions.md) 컨벤션을 따른다. DB 통합 검증은 [영속성](persistence-conventions.md), [Querydsl](querydsl-conventions.md) 컨벤션을 함께 따른다.
