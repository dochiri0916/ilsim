# 일심 MCP 전환 설계

Claude 앱(Claude Code)에서 명령하고, 모든 작업이 일심 MCP 서버를 거치도록 일심을 바꾸는 설계다. 사용자 결정은 [11장](#11-결정-기록)에 모았다. 1단계와 1a단계가 구현됐다.

## 1. 목표와 원칙

- 사용자는 Claude 앱에서 자연어로 명령한다. 코드 작업은 Claude 앱의 Agent가 한다.
- 일심은 작업 상태·단계·승인, 프로젝트 지식 조회, 정적 검사·JEV 판정, 완료 차단을 맡는다.
- 일심 작업을 시작하지 않으면 파일을 수정할 수 없고, 일심 검증을 통과하지 않으면 작업을 끝낼 수 없다.
- 기존 단계 계약(요구사항 → TC → 테스트 코드 → 구현), 사용자 승인, 정적 게이트는 유지한다.
- 어느 PC에서도 같은 설치 절차로 같은 기능을 쓴다. 기능을 PC 전용 설정에 두지 않는다.

## 2. 구성

```text
Claude 앱(Claude Code)
  ├─ 일심 플러그인: MCP 서버 등록 + 훅 + 스킬
  │    └─ 로컬 MCP 서버 `ilsim-runner mcp` (stdio, 프로젝트 폴더에서 실행)
  │         ├─ 파일·Git·빌드 실행, 정적 검사(아키텍처·컨벤션·위험·테스트 무결성·변이)
  │         ├─ JEV 호출(키는 서버에서 받음)
  │         └─ 일심 서버 API 호출
  └─ 훅: PreToolUse(수정 차단) · Stop(완료 차단) · UserPromptSubmit(안내 주입)

일심 서버(ilsim-server, 개인 PC 또는 사내 중앙 서버)
  ├─ 작업·단계·승인 상태, 비용·판정 이력, JEV 키, 규칙·학습
```

- MCP 서버는 코드가 있는 PC에서 돌아야 하므로 로컬 stdio로 둔다. 기존 Runner의 분석기·검사·서버 클라이언트를 그대로 쓰기 위해 `ilsim-runner`의 하위 명령으로 만든다.
- 중앙 서버 배포는 일심 서버만 옮긴다. 로컬 MCP는 설정의 서버 주소와 토큰으로 붙는다. 개인 PC는 같은 PC의 서버를 쓴다.
- 배포 단위는 Claude Code 플러그인이다. MCP 서버 등록(`.mcp.json`), 훅, 사용 스킬을 함께 담아 PC마다 설치 한 번으로 같은 구성이 된다.

## 3. 작업 흐름

1. 사용자가 Claude 앱에 요청한다. UserPromptSubmit 훅이 "이 저장소는 일심 관리 대상이며 먼저 `start_task`를 호출한다"는 안내를 넣는다.
2. Agent가 `start_task`를 호출한다. 서버가 작업을 만들고 MCP가 프로젝트의 활성 작업 상태를 기록한다.
3. Agent가 `next_step`으로 현재 단계의 지시(서버 `PromptTemplates`), 앞 단계 문서(요구사항·테스트 케이스), 이 작업에 고른 프로젝트 문서 지침 원문(6장)을 받는다.
4. Agent가 `get_guidelines`·`get_rules`로 필요한 자료를 더 조회하고 작업한다. 중간에 `check_change`로 정적 검사를 돌릴 수 있다.
5. Agent가 `submit_result`를 호출한다. MCP가 해당 단계의 게이트를 실행하고 결과를 서버에 보낸다.
   - 실패하면 구체적인 수정 사항을 돌려주고 Agent가 고친 뒤 다시 제출한다.
   - 승인 단계(요구사항·TC)는 사용자가 Claude 앱에서 승인해야 다음 단계로 간다(`approve_stage`·`reject_stage`, 매번 사용자 확인 창).
6. 마지막 단계가 통과하면 작업이 완료되고 활성 상태가 풀린다.

## 4. MCP 도구

| 도구 | 입력 | 결과 | 비고 |
|---|---|---|---|
| `start_task` | 요구사항, 기능 이름(선택) | 작업 ID, 브랜치, 첫 단계 지시 | 커밋하지 않은 변경이 있으면 거절, 작업 브랜치 `ilsim/<기능>-<ID 8자>`로 전환 |
| `next_step` | 없음(저장소의 활성 작업) | 단계, 지시, 허용 경로, 이전 피드백. 작업이 없거나 승인 대기·완료·차단이면 그 상태 | 상태 조회를 겸한다(별도 `status` 도구 없음, 사용자 결정 2026-10-24) |
| `get_guidelines` | 없음(저장소의 활성 작업) | 이 작업에 고른 문서 지침 원문과 출처, JEV 관련도 | 6장. `next_step`에 넣은 것과 같다 |
| `get_rules` | 없음 | 승인된 아키텍처·컨벤션 규칙과 위험 패턴 요약 | 기존 규칙 저장소 |
| `check_change` | 없음(작업 트리 기준) | 허용 경로·아키텍처·컨벤션·BLOCK 위험·테스트 무결성 위반, 참고용 위험 후보 | 차단하지 않음. 테스트·변이·독립 검토는 `submit_result` |
| `submit_result` | 요약(선택) | 통과·실패, 게이트별 결과, 수정 사항 | 7장 게이트. 실패는 서버에 보고하지 않고 수정 사항만 돌려준다(시도 횟수 상한으로 차단되지 않게) |
| `approve_stage` | 단계 | 승인 결과와 다음 단계 지시 | 사용자가 승인한다고 말했을 때만, 호출마다 사용자 확인 창 |
| `reject_stage` | 단계, 수정 사항 | 같은 단계의 새 지시(사유 포함) | 호출마다 사용자 확인 창 |
| `retry_task` | 지시(선택) | 같은 단계의 새 지시 | 차단(BLOCKED)된 작업만, 사용자가 다시 하자고 할 때 |
| `reopen_stage` | 단계(`TEST_CODE`), 고칠 점 | 그 단계의 새 지시(사유 포함) | 진행 중인 단계보다 앞의 통과한 코드 단계만, 호출마다 사용자 확인 창. 그 뒤 단계는 시도 1부터. 현재 단계의 미커밋 변경은 `git stash`로 보관했다가 그 단계를 다시 맡을 때 되살린다(사용자 결정 2026-10-25, ilsim 앱 E2E에서 구현 단계가 틀린 테스트 기대값 때문에 통과할 수 없었음) |
| `review_rules` | 없음 | 규칙·학습 메모리 후보의 상태와 근거 | 웹 규칙 화면 대체 |
| `decide_rules` | id 목록, approve·reject | 승인·거절 결과 | 사용자가 말했을 때만, 호출마다 사용자 확인 창 |
| `analyze_project` | 없음 | 아키텍처·컨벤션 분석 보고 | 웹 분석 버튼 대체, AI 검토 포함이라 몇 분 걸림 |

- 승인은 Claude 앱에서 한다(사용자 결정 2026-10-24, 웹 승인 제거). `approve_stage(stage)`·`reject_stage(stage, feedback)`를 두고, Agent는 산출물을 요약해 보여 준 뒤 사용자가 답했을 때만 호출한다. Agent가 스스로 승인하지 못하도록 PreToolUse 훅이 두 도구 호출마다 `ask`를 돌려 앱이 사용자 확인 창을 띄운다(허용 목록에 넣어도 다시 묻는다). `stage`가 현재 승인 대기 단계와 다르면 거절한다. 요구사항 문서의 `## 미결정 사항`에 질문이 남아 있으면 승인 대기 안내에 그 질문을 붙여, Agent가 승인을 묻기 전에 사용자에게 알리고 답을 `reject_stage`로 반영하기를 먼저 권하게 한다(2026-10-27, 실사용 요구사항 문서 7개 모두 질문 4~6개를 남긴 채 진행됨). 그대로 승인하면 테스트 케이스·테스트 코드·구현 단계 지시에 "정하지 않은 사항" 절로 그 질문을 넣고 추측해 만들지 말고 꼭 정해야 하면 멈추고 물으라고 한다(`RequirementCheck.openQuestions`).
- 도구 결과는 짧은 요약과 근거 위치를 주고 원문 전체는 넣지 않는다. 필요한 원문은 Agent가 파일을 직접 읽는다.

## 5. 강제(훅)

| 시점 | 동작 | 차단 조건 |
|---|---|---|
| UserPromptSubmit | 일심 안내와 활성 작업 요약을 컨텍스트에 추가 | 없음 |
| PreToolUse(Edit·Write·MultiEdit·NotebookEdit) | 활성 작업과 현재 단계에서 허용한 경로인지 확인 | 활성 작업 없음, 승인 대기 중, 단계 범위 밖 경로(예: 요구사항 단계에서 `src/` 수정) |
| PreToolUse(Bash) | 파일을 바꾸는 명령 패턴 검사 | 활성 작업 없이 저장소 안 쓰기·이동·삭제(저장소 밖 절대 경로로의 출력 저장은 허용, 따옴표 안 글자는 검사하지 않지만 셸 `-c`·`eval`·큰따옴표 안 명령 치환은 검사. here-document 본문도 데이터로 보지만 셸이 실행(`bash <<EOF`, `| sh`)하거나 따옴표 없는 구분자 본문에 명령 치환이 있으면 검사하고, 끝나지 않은 본문은 전체를 검사), 항상 `git commit`·`reset`·`rebase`·`cherry-pick`·`revert`·`restore`·`stash`(`list`·`show` 제외), 활성 작업 중 `git push`·`pull`·`merge`·`checkout`·`switch`·`branch -d` 등(작업이 끝난 뒤 병합·푸시는 허용, 2026-10-25 E2E에서 사용자가 터미널로 병합·푸시해야 했던 문제) |
| Git pre-commit(`ilsim-runner hook commit`) | `start_task`가 대상 저장소 `.git/hooks/pre-commit`에 설치(기존 훅이 있으면 설치하지 않고 알림) | Claude Code 환경(`CLAUDECODE=1`)에서 일어난 커밋. 일심 자체 커밋(`ILSIM_RUNNER=1`)과 사람의 터미널 커밋은 통과 |
| Stop | 활성 작업의 마지막 `submit_result` 상태 확인 | 변경이 있는데 제출하지 않음, 마지막 제출 실패, JEV가 누락으로 판정한 요구사항 있음 |

- 훅은 `ilsim-runner hook <시점>`을 실행한다. 활성 작업 상태는 `~/.ilsim/active/<저장소 경로 해시>.json`에 두고, MCP와 훅이 함께 읽는다. 훅 입력의 `cwd`로 저장소를 찾는다.
- 같은 저장소에서 두 세션이 동시에 작업하면 상태가 겹친다. 1차 구현은 저장소당 활성 작업 하나로 제한하고, 두 번째 `start_task`는 거절한다.
- 훅은 클라이언트 쪽 장치라 사용자가 끌 수 있다. 최종 강제는 실행 경계에 둔다: 일심 서버의 단계·승인 상태, 대상 저장소의 Git pre-commit 훅(`ilsim-runner hook commit`), CI의 `ilsim-runner check`.

## 6. 프로젝트 문서 지침(선택·주입·준수 판정)

목적: 등록된 프로젝트마다 그 프로젝트의 스펙·아키텍처·컨벤션 문서를 Agent가 반드시 읽고 지키게 한다. 어떤 언어·구조·문서 위치의 프로젝트에도 같게 적용한다(사용자 결정 2026-10-25). JEV가 매우 저렴하므로 판단은 JEV로 하고 벡터 DB는 쓰지 않는다.

- 문서 범위(프로젝트별): 그 저장소에서 Git이 추적하는 문서 파일(`.md`·`.markdown`·`.adoc`·`.rst`·`.txt`)과 사용자가 그 프로젝트에 등록한 추가 문서(`ilsim-runner docs add <id> <경로>`, 저장소 밖 파일·폴더 가능)만 쓴다. Git 추적 기준이라 무시 파일(`node_modules`·빌드 결과)과 서브모듈·하위 저장소 내용은 빠진다. 저장소 안에 다른 등록 프로젝트가 있으면 그 경로를 뺀다. 현재 작업의 `specs/<기능>/` 산출물과 사용자가 뺀 경로(`docs exclude`)도 뺀다.
- 구간: 문서를 제목 단위로 나누고(상위 제목을 함께 붙임) 긴 구간은 문단 경계에서 최대 4,000자로 자른다.
- 문서 거름(선택 전, 사용자 결정 2026-10-25): 문서마다 경로·제목 목록·첫 구간 앞부분을 JEV에 주고 두 가지를 묻는다. 따를 규칙 구간이 있는 문서인가(작업 기록·계획·분석·안내만 있으면 아니오, 기록 문서라도 작업 규칙 구간이 있으면 예), 요청이 건드리는 모듈에 적용되는가(다른 모듈 전용이면 아니오). 둘 중 작은 값이 0.2 이하인 문서는 구간을 묻지 않고 빼며, 남은 문서의 구간 관련도는 문서 점수를 넘지 않는다(지시 분량 한도 안에서 적용 문서가 먼저 들어가게 한다). JEV 점수는 같은 요청에 함께 든 항목에 따라 달라지므로 문서 거름은 문서 하나씩, 구간 선택과 준수 판정은 같은 문서의 구간끼리만(10개씩) 묶어 묻는다. 그래서 다른 문서를 넣거나 빼도 결과와 캐시가 바뀌지 않는다. JEV 입력 한도(약 32k 토큰, 실측 2026-10-25)에 맞춰 요청 하나의 분량을 한글 1·ASCII 0.5로 세어 22,000 이하로 묶고, 준수 판정의 diff는 12,000 이하로 자른다(잘리면 모두 애매로 보고 독립 검토). 요구사항 판정도 같은 한도를 따라 요구사항을 10개·분량 22,000 이하로 나눠 묻고, diff는 12,000 이하로 자른다(잘리면 누락 판정 없이 불확실).
- 선택(`start_task` 때, 작업당 한 번): 구간마다 JEV에 두 가지를 묻는다. 구간 자체에 따를 구체 규칙이 적혀 있는가(소개·배경·미결정 사항·빌드·배포 안내는 아니오), 요청이 만들거나 바꾸는 코드에 그 규칙이 적용되는가(한 기능만의 요구사항·테스트 명세는 그 기능을 바꿀 때만). 관련도는 둘 중 작은 값이고, 누락이 더 위험하므로 0.2 이하만 뺀다. 선택 결과는 작업별로 저장하고(`~/.ilsim/guides/<작업 id>.json`), 같은 요청·같은 문서면 JEV 캐시로 다시 묻지 않는다. 시작 전에 만든 작업은 첫 `next_step`에서 고른다. 요구사항 단계 뒤(테스트 케이스 단계부터)는 승인된 요구사항 문서(영향 범위·요구사항이 적힘)를 요청으로 삼아 다시 고르고, 문서가 바뀌면(되돌려 고친 경우) 또 고른다(`TaskGuide.basis`에 문서 해시, 선택 기록에 "승인된 요구사항 문서 기준").
- 지침은 타당성과 관계없이 따른다(사용자 결정 2026-10-25): 단계 지시·스킬·MCP 안내에 "불합리해 보여도 건너뛰거나 바꾸지 말고 그대로 따르고, 서로 충돌하면 멈추고 사용자에게 묻는다"를 넣고, JEV 선택·위반 질문은 규칙이 합리적인지 따지지 않는다. sandbox 실측: "새 public 메서드는 zz로 시작" 같은 임의 규칙도 선택(0.72)되고 어기면 위반 0.98, 지키면 통과.
- 승인 단계 안내(사용자 결정 2026-10-25): 요구사항·테스트 케이스 단계에서 지침 판정이 애매하거나(관련도 0.5 이상, 0.4~0.8) 판정하지 못하면 독립 검토 대신, 승인 대기 응답에 그 지침과 출처를 넣어 Agent가 승인을 묻기 전에 사용자에게 알리게 한다.
- 모듈 범위(2026-10-25): 빌드 파일(`build.gradle(.kts)`·`pom.xml`·`package.json`·`Cargo.toml`·`go.mod`·`pyproject.toml` 등)이 있는 최상위 디렉터리를 모듈로 보고, 모듈이 둘 이상이면 요청마다 JEV에 "이 요청이 그 모듈을 바꾸는가"를 한 번에 묻는다. 모듈 안 문서의 거름 점수는 그 확률을 넘지 않는다(모듈 밖 문서는 저장소 전체 문서로 본다). 아래 문서 참조로 요구된 문서는 다시 들어온다. ilsim 실측: runner·server·analyzer 요청에서 build-convention 문서가 빠지고 build-convention 요청에서만 들어가며, 선택이 158구간 안팎에서 57~110구간으로 줄었다.
- 문서 참조(사용자 결정 2026-10-25): 고른 구간이 다른 문서를 링크(`[..](경로)`)나 코드 표기(`` `경로.md` ``)로 가리키면, JEV에 "이 구간이 이 요청 작업에서 그 문서를 읽거나 따르라고 요구하는가"를 묻는다(구간 하나씩). 0.5 이상이면 그 문서 점수를 그 값까지 올리고, 거름에서 빠졌던 문서라면 구간을 다시 고른다. 예: `AGENTS.md`의 "code-risk-analyzer 작업은 먼저 분석기 참고서를 읽는다"는 analyzer 요청에서만 참고서를 살린다. 한 단계만 따라가고 참조의 참조는 따라가지 않는다.
- 주입: `next_step` 지시에 고른 구간 원문을 출처(파일·줄)와 함께 넣는다. 넣을 분량(최대 40,000자)을 넘는 구간은 출처만 적어 Agent가 직접 읽게 한다. Agent가 찾아 읽기를 기대하지 않고 지시에 직접 넣는다.
- 준수 판정(`submit_result`, 모든 단계): 고른 구간마다 "이 변경이 그 구간에 적힌 규칙을 직접 어기는가"를 묻는다(다른 구간의 위반은 세지 않는다). 0.8 이상이면 어긴 구간과 출처를 돌려주고 제출을 실패시킨다. 관련도 0.5 이상인 구간에 0.4 초과 0.8 미만이 있거나 판정을 못 하면(JEV 꺼짐·실패) 독립 검토를 하고, 검토 프롬프트에 해당 지침 원문을 넣는다. 판정은 단계 결정 기록 `GUIDELINE_CHECK`으로, 선택한 구간별 관련도(제외한 구간 포함)는 첫 제출의 `GUIDELINE_SELECT`로 남긴다. 애매 기준은 첫 E2E(지킨 코드가 0.23~0.31로 애매가 됨)와 위반 주입(위반 5건 모두 0.93 이상) 결과로 0.2에서 0.4로 올렸다(2026-10-25). 위반이 있는 변경에서 README 소개·이전 기능 스펙까지 위반으로 나오던 오경보는 두 질문 선택·구간 한정 판정·관련도 0.5 기준으로 없앴다(sandbox 실측: 23구간 중 10개 선택, 위반 주입 diff는 실제 위반만 8건·애매 0, 지킨 diff는 위반·애매 0, 이전 기능을 바꾸는 요청은 그 스펙을 고른다, 2026-10-25). `ilsim-runner guidelines <id> "<요청>" [기준]`으로 실제 JEV의 선택과 작업 트리 diff 위반 판정을 바로 볼 수 있다. 항목 판정·재질문(2026-10-27): 목록·문단·표 행이 둘 이상인 구간은 항목(목록 항목에는 바로 앞 문단을 붙임)마다 묻고 구간 확률은 항목 최댓값으로 한다. 1차 확률이 0.2 이상 0.8 미만인 항목은 다른 구간 없이 하나씩 다시 물어 그 값을 쓴다(같은 구간·변경이라도 함께 묶인 구간에 따라 0.74와 0.30으로 갈렸다). 질문 state에는 일심 단계 작업이라는 맥락과 단계 설명(구현 단계 diff에는 앞 단계에서 쓴 테스트가 없다 등)을 넣는다.
- JEV가 꺼져 있으면 문서를 고르지 못하므로 문서 목록만 지시에 넣고 Agent가 직접 읽게 하며, 구현·테스트 코드 단계는 독립 검토를 한다.
- 문서 규칙 정적 변환(사용자 결정 2026-10-27): `analyze_project`(`doc-rules <id>`) 때 JEV가 규칙 문서·규칙 구간으로 고른 구간(문서 점수 0.2 초과, 구간 0.4 이상)만 Claude가 프로젝트 디렉터리 구조(디렉터리·패키지·대표 타입, 최대 60개)를 함께 보고 정해진 규칙 종류(`doc-forbidden-import`·`doc-required-annotation`·`doc-forbidden-annotation`·`doc-name-pattern`·`doc-forbidden-code`·`doc-required-code`·`doc-file-location`·`doc-max-size`·`doc-max-occurrences`)로 옮긴다. 원문 인용이 구간에 없거나 형식이 틀리면 버리고, JEV가 원문 그대로가 아니라고 본 규칙(0.4 미만)은 빼서 JEV 판정 문장으로 남긴다. 원문 일치는 후보를 묶어 한 번에 묻고, 0.15 이상 0.6 미만으로 애매한 후보만 따로 다시 물어 두 값을 평균한다. 질문에는 범위(scope·path를 넓히거나 좁혔는지), 여러 규칙 중 하나만 옮긴 것, 역할 이름을 애너테이션·구조의 경로로 가린 것, 새 코드 규칙을 모든 파일 대상으로 옮긴 것의 판단 기준을 넣었다(2026-10-27 평가, 후보 59개 2회: 옳은 규칙 버림 0·틀린 규칙 통과 0. 묶음 판정만 쓰면 1·2, 후보마다 따로만 물으면 기준 0.3에서 틀린 규칙 통과 5). 옮긴 규칙은 그 프로젝트 전용 문서 지침 검증기(`~/.ilsim/projects/<id>/doc-rules.json`, `doc:` id의 BLOCK 후보, 사용자 결정 2026-10-27로 컨벤션 규칙과 분리)에 저장되고 사용자가 `decide_rules`로 승인해야 적용된다. 제출 때는 별도 단계 `doc-rules`가 바꾼 파일에서 HEAD에 없던 위반만 막는다(기존 위반은 기록만). 구간 내용 해시로 캐시해 바뀐 구간만 다시 옮긴다. 옮기지 못한 문장은 지금처럼 JEV 준수 판정으로 확인한다. Java·Kotlin 소스만 검사하고, Java·Kotlin 소스와 Gradle·Maven 빌드 파일이 모두 없는 프로젝트(TypeScript 등)에는 문서 지침 검증기를 만들지 않는다.
- 판정 평가(2026-10-27): `ilsim-runner jev-eval guidelines`가 정답 세트(`ilsim-runner/corpus/jev-guideline`, 실제·가상 프로젝트 4개, 구간 67·요청 11·변경 63·문서 규칙 후보 21)로 운영과 같은 질문의 정확도를 잰다. 결과(2회 반복, 판정이 바뀐 사례는 위반 판정 476건 중 5건): 최종 선택 놓침 0·오경보 5/104, 규칙 구간 거름(문서 규칙) 0/0, 참조 0/0, 변경 차단은 규칙을 어긴 변경 49개 중 36개를 막고 준수 변경 14개 중 0~1개를 막음(경계값 0.81), 못 막은 13개 중 8~10개는 애매(독립 검토)로 넘어가고 3~5개는 그냥 통과한다. 놓침은 여러 규칙이 든 긴 구간 안의 한 줄 위반(묶음에 다른 구간이 함께 들면 0.74→0.30), 경로·위치 규칙, 영어로 쓴 `@DisplayName` 같은 세부 조건에서 나온다. 모듈 질문은 요청에 모듈 이름이 없으면 틀린다(정확도 75%). 이 결과로 문서 규칙 원문 일치 기준을 0.5→0.3으로 내렸고(옳은 규칙 0.14~0.47, 틀린 규칙 최대 0.14), 위반 질문에 "앞 단계에서 이미 만든 코드(구현 전에 쓴 테스트 등)가 diff에 없는 것은 위반이 아니다"를 넣어 구현 단계 오판정을 없앴다. 나머지 기준은 놓침 없이 바꿀 근거가 없어 그대로 둔다. 이어서 항목 판정·재질문·단계 설명을 넣은 뒤(4차, JEV 745회): 위반 변경 49개 중 43개 차단·5개 독립 검토·1개 통과(영어로 쓴 `@DisplayName`), 준수 변경 14개 중 오차단 0·검토 8, 위반 판정 AUROC 0.96→0.98. 항목 분할만으로는 효과가 거의 없고(37/49) 재질문이 효과를 낸다. 애매 기준 0.3이나 재질문 하한 0.1은 이 세트에서 더 잡는 위반 없이 검토·호출만 늘어 0.4·0.2를 유지한다. 2회 반복 확인 측정에서도 두 반복의 차단·검토·통과가 같았다(AUROC 0.983·0.985).

- JEV 요구사항 충족 판정(평가 결과: 누락 놓침 0, 오경보 1/102): 요구사항마다 충족 확률을 구해 0.2 이하는 누락으로 보고 제출을 실패시킨다. 판정과 이후 실제 결과(검토 지적·사용자 반려·회귀)를 함께 기록해 임계값을 보정한다.
- JEV 영향 범위 판정(사용자 지시 2026-10-27): 요구사항 문서는 `## 영향 범위`에 만들거나 고칠 파일을 저장소 기준 경로로 적는다(서버 요구사항 단계 작성 규칙). 테스트 코드·구현 단계 제출 때 바뀐 파일 중 문서 어디에든 경로·파일 이름·클래스 이름이 적혔거나 영향 범위 절의 디렉터리·패키지 아래인 파일은 정적으로 통과시키고(`ScopeCheck.listed`), 나머지만 파일별로 "요구사항을 구현·테스트하는 데 필요한 범위 안인가"를 JEV에 묻는다(`ScopeCheck`, 단계 설명·문서·바뀐 파일 목록을 함께 줌). 0.2 이하면 범위 밖으로 제출을 실패시키고(되돌리거나 꼭 필요하면 사용자에게 묻게 함), 0.8 미만은 불확실로 구현 단계 독립 검토 조건에 넣는다(`validation["scope"]`, 결정 기록 `SCOPE_CHECK`의 `STATIC`·`JEV`). 평가(`jev-eval scope`, `corpus/jev-scope` 6사례·파일 39개, 2회): 범위 밖 17개 모두 0.16 이하, 범위 안 22개 모두 0.65 이상(AUROC 1.00), 기준 0.2에서 범위 안을 막은 파일 0, 문서에 안 적힌 도우미 메서드 1개만 불확실. sandbox E2E에서 관계없는 새 클래스를 0.08로 막고 지운 뒤 통과했다.
- JEV 위험 선별은 평가에서 오경보가 많아 확정에 쓰지 않는다. `check_change` 결과에 확률만 참고로 보인다.
- 독립 검토(현재 `ai-audit`, 사용자 결정 2026-10-24: 조건부)는 작업한 Agent와 다른 Claude 호출이다. 작업한 Agent의 자기 평가는 검토로 세지 않는다.

  - 구현 단계: JEV 판정 중 0.2 초과 0.8 미만(불확실)이 있거나, 위험 후보가 있거나, diff가 기준(초기값 300줄)보다 클 때만 검토한다. 셋 다 아니면 검토 없이 통과한다.
  - 표본: 검토를 건너뛴 구현 단계의 일부(초기값 20%)를 검토해 놓친 문제를 찾는다. 결과(건너뜀·표본 검토·지적 내용·이후 사용자 반려·회귀)를 작업 이력에 남기고, 놓친 문제가 나오면 조건과 기준을 조정한다. 표본 비율과 기준은 프로젝트 설정으로 바꾼다.
- 구현(2026-10-24, 3단계): `RequirementCheck`가 요구사항 문서(`~/.ilsim/projects/<id>/specs/…/requirements.md`)의 `REQ-n` 줄을 요구사항으로 읽어 구현 단계 diff(최대 60,000자)와 함께 JEV에 묻는다. diff가 잘리면 누락 판정을 내리지 않고 불확실로 둔다. 테스트는 앞 단계에서 커밋돼 구현 diff에 없으므로, 질문에 단계 설명을 넣고 요구사항 중 테스트 자체에 관한 부분(테스트 작성·이름·애너테이션·분리·통과)은 충족으로 보고 나머지 동작만 판정하게 한다(2026-10-27, sandbox E2E에서 "테스트마다 `@DisplayName`" 요구사항을 누락으로 봐 완성된 구현을 막은 결함. 평가 127칸×2회: 충족을 누락으로 본 칸 25→4(남은 4칸은 다른 요구사항이 실제로 빠진 변경에서만), 누락 놓침 0 유지, AUROC 0.93→0.98, 평가 세트에 테스트 요구사항 사례 `greet-all` 추가와 `case.json`의 `tests` 목록). JEV가 꺼졌거나 실패하면 판정 없음(`requirements=UNKNOWN`)으로 보고 독립 검토를 한다. 판정·검토 생략·표본 결정은 단계 결정 기록(`REQUIREMENT_CHECK`, `CHANGE_AUDIT`의 `AGENT`·`SKIP`·`SAMPLE`)으로 서버에 남는다. 표본 여부는 실행 ID로 정해 같은 실행은 같은 결과가 난다. 비율과 diff 기준은 Runner 프로젝트 설정 `auditSampleRate`·`auditMaxDiffLines`로 바꾼다. 서버 `claim`은 코드 단계 시작 때 `ReviewCostPolicy.grant`로 검토 모델 비교 표본을 예약한다(기본 예산 0이라 설정 전에는 예약하지 않음).

## 8. 서버·기존 구성 변경

- 진입점은 Claude 앱 하나다(사용자 결정 2026-10-24, Claude 앱 원격 사용 포함). 작업은 MCP `start_task`로만 만든다.
- MCP용 API는 Runner 토큰으로 인증하는 `/runner/api` 아래에 둔다: `POST /projects`(프로젝트 등록), `POST /tasks`(Claude 앱 작업 생성), `GET /tasks/{id}`(상태), `POST /tasks/{id}/claim`(단계 시작, 실행 중이면 같은 실행 반환), 결과 보고는 기존 `POST /tasks/{id}/result`. 작업에 `agent`(`runner` | `claude-app`)를 두고, Runner `poll`과 라우팅 학습은 `claude-app` 작업을 제외한다.
- 모델·effort는 Claude 앱에서 사용자가 정한다. 비용은 Claude 앱 사용량을 받을 수 없으므로 MCP·JEV·독립 검토 비용만 집계한다.
- 웹은 없앴다(사용자 결정 2026-10-25). 규칙·학습 메모리 승인은 MCP `review_rules`·`decide_rules`(매번 사용자 확인), JEV 키는 `ilsim-runner jev-key set|delete|status`(서버 `/runner/api/secrets/jev`)로 한다. 서버의 로그인·세션·계정·2단계 인증과 웹 API, `ilsim-web` 모듈을 지웠고 Runner 토큰 필터만 남겼다.
- Runner의 `run`(서버 작업을 받아 Claude CLI로 실행)과 이 경로에서만 쓰는 기능을 제거한다: 작업 폴링·실행(`TaskExecutor`), 작업용 Claude CLI 실행, 모델·effort 라우팅(`ModelSelector`·비용 라우팅·`RoutingReview`), DeepSeek 공급자 계정, 여러 Claude 계정 선택. 독립 검토의 Claude 호출(`ReviewRouter`·`ClaudeCli`의 검토용 부분)은 남긴다.
- 제거 시점은 10장 1단계 E2E가 통과한 뒤다. 그 전에 지우면 작업을 실행할 경로가 없어진다.

## 9. 외부 전송과 회사 PC

- 외부로 나가는 것: JEV(TypeSafe)에 코드 발췌·diff·요구사항, 독립 검토의 Claude 호출.
- 문서 지침 선택·준수 판정은 문서 구간 원문을 JEV에 보낸다.
- 프로젝트 설정으로 JEV를 끌 수 있게 한다. 끄면 JEV 판정 대신 독립 검토로 동작한다.

## 10. 구현 단계와 수용 기준

| 단계 | 내용 | 수용 기준 |
|---|---|---|
| 1 | `ilsim-runner mcp`(stdio)와 `start_task`·`next_step`·`submit_result`, 서버 `agent` 구분·MCP API, 훅(PreToolUse·Stop), 플러그인 묶음 | sandbox에서 Claude 앱으로 4단계 E2E 통과. 작업 없이 수정하면 차단, 제출 전 종료하면 차단, 승인 전 다음 단계 진행 불가 |

| 2 | `check_change`·`get_rules`, pre-commit 훅 | 위반 주입 시 검출, 훅을 끄고 커밋해도 pre-commit에서 차단 |

| 4 | 6장 프로젝트 문서 지침: 문서 범위·구간, JEV 선택, 단계 지시 주입, 제출 시 준수 판정 | 다른 프로젝트 문서가 섞이지 않음, 지침 위반 주입 시 제출 실패, 언어가 다른 시험 프로젝트에서 같은 흐름 통과 |
