### 반영한 내용

- 세션·모델별 누적 비용과 토큰은 차액만 집계한다. CLI 버전, 실행 ID, 호출 목적, 실제 모델 사용량, effort, 입력·출력·cache 토큰을 저장한다. 이전 CLI의 실행별 비용과 구분하고, 누적값 감소·이전 형식에서 넘어온 세션의 기준값 부족은 미확인으로 남긴다. 과거 원본이 없는 집계액은 `costIsUnverified`로 구분해 절감률 계산에서 제외하며, 추정으로 소급 수정하지 않는다.
- 오류 결과의 비용을 보존하고, 중단 시 확인한 assistant 입력·cache 토큰은 message ID로 중복을 제거해 복구한다. 복구치는 `RECOVERED`이며 출력 placeholder와 USD 추정치를 확정 비용에 합치지 않는다. JEV·프로젝트 분석도 저장·집계하고 미확인 호출이나 실행 중 작업이 있으면 합계를 하한으로 표시한다.
- 서버 실행 ID와 완료 이력으로 결과를 멱등 처리한다. 중지·재배정 후 늦은 결과는 원래 단계의 비용에만 반영한다. Runner는 결과·사용량·진행 이벤트를 로컬에 보관하고 재전송하며, 상태·비용·검증 로그는 수신 확인 전에 저장한다. 진행 전송은 Claude 출력 소비와 분리했고 HTTP timeout과 이벤트 ID를 적용했다.
- 작성 완료 지점의 코드·요구사항·규칙·명령·환경이 유효하면 검증 환경 오류 후 작성부터 반복하지 않는다. 코드 수정이 필요한 실패는 다시 작성한다. 검토·커밋 완료 기록과 Git tree도 확인해 보고 장애 후 Agent를 다시 실행하지 않는다. 실행 파일·명령 문법 오류는 작성 전에 검사하고, 세션 부재가 확인된 오류만 새 세션으로 대체한다.
- 단발 검토와 작성 모두 `--tools`, MCP 차단·명시적 구성을 적용했다. 기존 인증·프로젝트 지침·메모리는 유지한다. 큰 프롬프트는 stdin으로 전달한다.
- 정적 BLOCK·테스트 무력화 검사·테스트 실행 뒤에 위험 AI 검토를 배치했다. 위험 의견은 성공한 묶음마다 잠금·원자적 저장으로 보존한다. 지적 문구·권고·정책을 지문에 넣고 같은 파일의 겹치는 검토 발췌를 합친다.
- 변경 검토의 빈 응답·필수 필드 누락은 검토 완료로 처리하지 않는다. 규칙 검토도 후보가 불완전하면 완료 해시를 저장하지 않는다. 변경 검토 입력·정책·규칙·실행 환경을 포함한 캐시를 추가했고, reviewer·effort·정책이 달라지면 규칙 검토를 다시 한다. 개별 규칙의 관측과 공유 의존 근거가 유효한 의견은 부분 재사용하되 전체 누락·충돌 검토는 매번 유지하고 기존 의견도 수정할 수 있게 했다. 문서 등 공통 근거를 변동 요약보다 앞에 배치했다. 요구사항·diff·관련 테스트의 뒷부분을 잘라 버리던 제한도 제거했다.
- 위험 JEV를 묶음 질문으로 전환하고 근거 충분성도 함께 평가한다. 동일 근거·질문·정책의 판단을 재사용하며 연속 장애에는 circuit breaker와 Agent fallback을 쓴다. 프로젝트 분석 전에 서버 JEV 키를 갱신한다. 규칙 검토에는 JEV 완료·미해결 후보 이관 경로를 추가했다. 새로운 문제를 찾는 독립 변경 검토는 유지한다.
- 작성은 Haiku·Sonnet·Opus × 지원 effort 5종을 함께 평가하고 품질 조건을 만족하는 후보의 예상 완료 비용을 비교한다. 실패 횟수만으로 Opus에 고정 승격하지 않는다. 서버에 저장한 실행 이력·검증·승인·회귀 피드백을 보정에 사용하고 환경 오류를 분리한다. 저장된 유사 실행을 주기적으로 비교하며 이 비교 자체의 추가 AI 호출 비용은 0이다. 저가 후보는 충분한 성공 표본과 기준 경로 대비 품질 조건을 통과해야 기본 정책에서 채택된다.
- 변경·위험·아키텍처·컨벤션 검토도 별도 모델·effort 선택에 연결했다. 외부 근거로 확인한 정확·누락·오탐 피드백을 서버에 보존하고 같은 목적·작업군에서 기준 경로보다 품질이 나빠지지 않은 조합만 자동 채택한다. 부정 피드백은 다음 비교 주기를 기다리지 않고 반영하며 보정 비활성화·정책 버전 변경으로 되돌릴 수 있다. 작성 성공이나 두 모델의 단순 응답 일치를 검토 정확도의 증거로 쓰지 않는다.
- 선택적으로 독립 변경 검토의 기준 응답과 저비용 조합을 제한된 표본에서 비교한다. 서버가 주기·횟수·예산 예약을 저장하고 Runner가 입력 예상 비용과 CLI의 `--max-budget-usd`를 적용한다. 비교 응답·연결 ID·비용은 보존하되 실제 작업 판정에는 기준 응답을 쓴다. 표본 예약은 작업 삭제·재시작 뒤에도 보존하며, 비용 불명·실패·캐시 적중으로 사용하지 않은 예약도 다시 발급하지 않는다. 기본 추가 유료 평가 횟수·총예산은 0이다.
- 통계에 목적·모델·effort·단계별 비용·토큰·실행 결과와 검토 정확·누락·오탐, JEV 완료·Agent 이관·결과 재사용 이력을 추가했다. 검토 모델을 작성 모델 승격으로 세지 않는다. 금액 상한으로 본 작업을 끊는 대신 선택적인 작업 비용 알림을 제공한다. 기존 메모리의 지문 중복 제거·근거 소멸 확인·사용자 오탐 집계는 결정론적인 정적 처리로 유지한다.

회귀·품질 피드백은 `POST /api/tasks/{id}/executions/{executionId}/feedback`에 `{"passed":false,"reason":"회귀 검증 근거"}`를 보내 기록한다. 실행 ID와 원래 선택 정책·검증 결과가 함께 보존된다.

검토 정확도는 별도 근거로 확인한다. 작업 상세의 `stages[].usage[]` 또는 `GET /api/projects/{id}/reviews`에서 호출 ID·원문·표본 연결을 확인하고 `POST /api/tasks/{id}/reviews/{usageId}/feedback` 또는 `POST /api/projects/{id}/reviews/{usageId}/feedback`에 `{"passed":false,"missed":true,"falsePositive":false,"reason":"누락을 재현한 검증 근거"}`를 보낸다. 정확한 검토는 `passed:true`로 기록한다. JEV의 확률이나 기준 응답과의 일치만으로 자동 통과 라벨을 만들지 않는다. 검토 품질과 예약액은 `/api/stats`와 웹 통계에서도 확인할 수 있다.

추가 표본의 예산 옵션은 CLI의 요청 실행 단위로 적용되므로 단일 요청의 실제 비용이 예약액을 넘을 가능성까지 엄격히 차단하는 결제 한도는 아니다. 실제 비용은 전부 집계하며 예약액은 재사용하지 않는다. 본 작업의 작성·검토는 이 추가 평가 예산으로 중단하지 않는다.

서버와 Runner를 함께 업데이트·재시작해야 새 실행 ID·재전송 계약이 적용된다. DB가 없으면 새 유료 실행 배정을 보류한다. 기존 저장본은 기본값으로 읽으며, 새 프로젝트 비용 필드와 이벤트 ID 컬럼은 기존 테이블에 추가한다.

### 계산 가능한 절감률

2026-10-18 [공식 표준 가격](https://platform.claude.com/docs/en/about-claude/pricing#model-pricing)의 **cache를 제외한 동일 입력·출력 토큰**, Haiku 입력 100,000토큰 이하 조건이다.

| 비교 | 계산 | 단가 기준 절감률 |
|---|---|---:|
| Sonnet → Haiku | `1 - 0.10 / 2 = 1 - 0.50 / 10` | **95%** |
| Opus → Sonnet | `1 - 2 / 4 = 1 - 10 / 20` | **50%** |
| Opus → Haiku | `1 - 0.10 / 4 = 1 - 0.50 / 20` | **97.5%** |
| 누적 비용 집계 예시 `$0.25 → $0.15` | `1 - 0.15 / 0.25` | 표시액 40% 보정, 실제 사용 절감 0% |

기존 비용 중 Haiku로 옮기는 비중을 `q`라고 하면 위 조건의 단가 효과는 `95 × q%`다. 작성 4회·검토 2회의 비용이 각각 같다는 예시에서 2회 상당을 전환하면 31.67%, 4회 상당은 63.33%다. 실제 Agent 실행별 토큰·cache·effort·재시도는 서로 다르고 JEV·검증 비용도 추가되므로 운영 절감률은 이보다 달라질 수 있다.

위험 후보 20개를 JEV로 묶으면 HTTP 요청은 최대 20회에서 1회로 **95% 감소**한다. 근거 충분성 질문을 추가했으므로 질문 수와 청구액이 같은 비율로 줄었다고 계산하지 않는다. 유효한 캐시 적중·완료 지점 재개는 해당 중복 Agent 호출을 생략하지만 전체 작업에서의 비중은 운영 자료가 필요하다.

실측 비교에는 [완료 작업당 비용 비교 도구](../scripts/ai_cost_report.py)를 사용한다.

```bash
python3 scripts/ai_cost_report.py --before before.json --after after.json
```

각 파일은 기간별 `{"completedTasks":10,"costUsd":1.2,"unknownCalls":0,"costIsLowerBound":false,"costIsUnverified":false}` 집계 또는 작업 목록과 총비용을 함께 가진 JSON이다. 새 `/api/stats`에도 완료 건수를 포함해 같은 형식으로 비교할 수 있다. 양쪽에 JEV·프로젝트 분석·실패·재시도·비교 표본 비용을 동일하게 포함한다. 계산식은 `100 × (1 - 변경 후 완료 작업당 비용 / 변경 전 완료 작업당 비용)`이다. 비용 미확인·하한·이전 원본 미검증 집계·완료 작업 부족·기준 비용 0이면 절감률은 `null`이다. 작업 목록만 있으면 프로젝트 분석 비용 포함 여부가 불명확해 확정 비율을 내지 않는다.

**실제 운영 절감률은 아직 측정하지 않았다.** 단위 테스트는 실행·계측·보정·표본 제한 계약을 검증하며 모델 판단 품질의 동등성을 입증하지 않는다. 검토 보정·유료 표본 제한·규칙별 재사용은 구현했지만 실제 모델 비교와 외부 품질 라벨은 수집하지 않았다. 따라서 미검증 작성·검토 조합과 JEV 규칙 완료를 운영 기본값에서 자동 활성화하지 않는다. 개방형 변경 검토와 사용자 메모리 승인은 유지하며, 새 의미적 메모리 판단처럼 현재 정적 근거만으로 끝낼 수 없는 기능까지 JEV가 전면 대체했다고 보지 않는다.

### 이번 적용의 검증

변경한 Kotlin 소스·테스트를 로컬 compiler와 저장된 의존성으로 재컴파일했다. Runner JUnit **144/144건 통과**, 서버 **139건 중 138건 통과**, 비용 비교 도구 **6/6건 통과**, 웹 TypeScript·Vite 빌드 통과다. `JpaTaskStore`의 final 클래스·메서드를 프록시 가능하게 바꾸고 실제 Spring CGLIB 프록시의 메서드 위임·트랜잭션 롤백을 검증했다. 서버의 나머지 1건은 `contextLoads`로, sandbox의 MySQL 소켓 접근 제한 때문에 실패했다. Gradle Wrapper도 파일 잠금 소켓 제한으로 빌드를 시작하지 못했다. Gradle 전체 빌드·실제 유료 AI·모델 간 품질 비교·운영 청구 대조의 통과를 주장하지 않는다.

## 최초 분석의 전제

추가 점검은 같은 날의 미커밋 작업 트리(작업 중지·사용자 지시를 통한 세션 재개 포함)를 기준으로 했다. 최초 작성 시점에는 아래 추가 절감안을 구현하지 않았으며, 호출 횟수·동작 재현과 실제 운영 절감 효과를 구분했다.

**판정: 부분 최적화 상태다. 정적 검사·선별·일부 결과 재사용은 구현되어 있지만, 비용 집계 오류와 모델 선택·검토 실행 방식에 개선 여지가 있다. 기능을 유지하는 최적화는 비용 계측 교정부터 시작하는 것이 적절하다.**

실제 청구서, 운영 서버의 환경 변수, 기간별 작업 데이터를 조회하지 않았다. 따라서 월 비용이나 프로젝트 전체 절감률을 확정할 수는 없다. 아래 모델 설정은 코드 기본값이며 운영 설정과 다를 수 있다.

## 현재 호출 구조

- 요구사항 → 테스트 케이스 → 테스트 코드 → 구현의 네 단계마다 Claude Code를 실행한다. 요구사항과 테스트 케이스는 사용자 승인을 받는다.
- 테스트 코드·구현 단계는 검증을 통과하면 별도의 AI 변경 검토를 실행한다. 정상 경로의 기본 구성은 작성 4회 + 변경 검토 2회로, 최소 6회의 CLI 실행이다. 각 CLI 실행 안의 실제 모델 요청 수는 도구 사용 등에 따라 더 많다.
- 승인된 위험 규칙의 새 후보에는 JEV 선별과 추가 Claude 검토가 붙는다. 프로젝트의 아키텍처·컨벤션 분석에도 문서 선택용 JEV와 규칙 검토용 Claude가 사용될 수 있다.
- 작성 모델의 최소 등급은 기본 `sonnet`, effort는 `medium`이다. Runner의 검토 모델은 `SONNET`, effort는 `medium` 상수다.

## 우선 교정할 비용 계측

### 1. 세션 재개의 누적 비용 중복 합산

Claude Code `2.1.277`부터 `--resume` 결과의 `total_cost_usd`에는 이전 세션 비용이 포함된다. 현재 PC의 버전은 `2.1.302`이므로 이 계약이 적용된다. [공식 비용 추적 문서](https://code.claude.com/docs/en/agent-sdk/cost-tracking#accumulate-costs-across-multiple-calls)

현재 [ClaudeCost.parse](../ilsim-runner/src/main/kotlin/com/dochiri/ilsim/runner/ClaudeAgent.kt#L16)는 값을 그대로 읽고, [TaskExecutor.accumulate](../ilsim-runner/src/main/kotlin/com/dochiri/ilsim/runner/TaskExecutor.kt#L81)와 [Task.report](../ilsim-server/src/main/kotlin/com/dochiri/ilsim/task/domain/Task.kt#L74)는 이를 실행별 추가 비용으로 합산한다.

동일 세션의 첫 결과가 `$0.10`, 후속 대화 결과가 누적 `$0.15`라면 총비용은 `$0.15`인데 현재 집계는 `$0.25`다. 기존 컴파일 코드에 이 두 결과를 전달하는 방식으로 재현했다. 실제 유료 Claude 호출을 통한 재현은 하지 않았다.

추가 점검 시점에는 중지·실패한 다른 단계도 사용자 지시와 함께 재시도하면 같은 세션을 재개한다. 차액 집계는 요구사항 대화뿐 아니라 모든 `--resume` 경로에 적용해야 한다.

개선: 세션별 직전 누적 비용과 CLI 버전을 저장하고 새 비용의 차액만 반영한다. 세션 교체·리셋·실패를 구분하고, 결과 재전송도 실행 식별자로 중복 반영되지 않게 해야 한다. 모델별 누적 내역도 같은 기준으로 처리한다.

### 2. 비용 누락과 불명확한 합계

- [ClaudeCli.askWithCost](../ilsim-runner/src/main/kotlin/com/dochiri/ilsim/runner/ClaudeCli.kt#L24)는 비정상 종료 시 비용을 파싱하기 전에 예외를 던진다. 비용이 포함된 오류 결과도 집계에서 빠질 수 있다.
- 작성 실행이 시간 초과 등으로 마지막 `result`를 남기지 않으면 비용은 `null`이다. 서버는 이를 합계에 더하지 않지만, 비용 미확인 호출 수를 별도로 보존하지 않아 알려진 비용만 표시된다.
- JEV 어댑터는 평가 응답에서 답만 추출하고 사용량을 집계하지 않는다. 프로젝트 분석 비용은 `CostTally`가 보고서 문자열에 남기지만 작업 통계에는 포함되지 않는다.

개선: 호출 목적·실행·세션·실제 모델별로 입력/출력/cache 토큰, 알려진 비용, 비용 미확인 상태를 기록한다. JEV와 프로젝트 분석도 포함한다. 미확인 호출이 있으면 합계가 하한임을 표시한다. 오류 결과의 비용도 보존하고, 중단된 실행은 마지막 확인 사용량을 복구하되 확정치와 구분한다.

근거: [Task.report](../ilsim-server/src/main/kotlin/com/dochiri/ilsim/task/domain/Task.kt#L78), [TypeSafeJevGateway](../ilsim-server/src/main/kotlin/com/dochiri/ilsim/jev/adapter/out/typesafe/TypeSafeJevGateway.kt#L57), [Runner Jev](../ilsim-runner/src/main/kotlin/com/dochiri/ilsim/runner/jev/Jev.kt), [분석 결과 구성](../ilsim-runner/src/main/kotlin/com/dochiri/ilsim/runner/Main.kt#L450).

### 3. 검토 모델을 모델 승격으로 집계

[Stats.of](../ilsim-server/src/main/kotlin/com/dochiri/ilsim/task/domain/TaskStats.kt#L32)는 비용이 기록된 모델이 두 개 이상이면 승격 단계로 센다. 따라서 재시도 없이 Opus로 작성하고 Sonnet으로 검토해도 승격 1건으로 집계된다. 이 경로도 재현했다.

개선: 작성 실행의 라우팅 이력에서 실제 등급 상승을 계산하고 검토 호출은 별도로 구분한다. 현재 승격 지표만으로 모델 선택 효율을 평가하면 판단이 왜곡된다.

### JEV 확대 시 평가 자체의 중복 방지

- 같은 근거를 쓰는 선별·위험·모델·effort 질문은 식별 가능한 질문으로 묶고, 이미 유효한 판단은 다시 묻지 않는다. 이미 검증된 정책으로 처리 경로를 정할 수 있으면, JEV를 호출할지 판단하기 위한 별도 AI 호출을 추가하지 않는다. 독립 검토는 작성자의 자기평가와 분리한다.
- 현재 [JevRiskScreen](../ilsim-runner/src/main/kotlin/com/dochiri/ilsim/runner/jev/JevRiskScreen.kt)은 앞선 JEV 요청이 실패해도 다음 후보를 계속 요청하고, [Jev](../ilsim-runner/src/main/kotlin/com/dochiri/ilsim/runner/jev/Jev.kt)는 요청별 timeout·retry만 둔다. 연속 장애에는 잠시 호출을 멈추고 유효한 캐시·기존 Agent fallback을 사용한 뒤 제한된 요청으로 회복을 확인한다. 검사 대상과 검토 범위는 줄이지 않는다.
- 묶음 요청은 HTTP 횟수 감소와 과금 감소를 구분해 측정한다. 질문 수·입력 크기에 따라 과금이 유지되거나 증가할 수 있다. `JEV 평가·재평가 + Agent fallback + 재작업 + 표본 검증` 전체 비용과 지연을 비교하고, 품질 기준을 충족하는 정책만 적용한다.

### 재사용 확대 전에 보완할 기능 유지 조건

1. **응답 형식과 검토 완료를 구분한다.** 현재 `ChangeAudit.parse("{}")`는 PASS가 된다. 규칙 검토도 `{}`를 받으면 의견이 없는 규칙을 남긴 채 전체 검토 해시를 저장해 다음 호출을 생략한다. 요구한 후보 ID·필수 필드·판정·근거를 검증하고, 누락된 항목만 재질문하거나 UNKNOWN으로 남겨 기존 실패·승인 정책에 연결해야 한다. 실패를 PASS로 바꿔 호출이 줄어드는 것은 절감으로 세지 않는다. `--json-schema` 적용은 후보지만 출력의 `structured_output` 처리와 실제 후보별 완전성 검증이 함께 필요하다. [ChangeAudit](../ilsim-runner/src/main/kotlin/com/dochiri/ilsim/runner/audit/ChangeAudit.kt), [규칙 검토](../ilsim-runner/src/main/kotlin/com/dochiri/ilsim/runner/architecture/ArchitectureReviewer.kt), [공식 구조화 출력 안내](https://code.claude.com/docs/en/headless#get-structured-output)
2. **현재 캐시도 실제 판단 입력과 정책에 맞춰 무효화한다.** 아키텍처·컨벤션 해시는 reviewer·effort·프롬프트·평가 정책 버전을 포함하지 않는다. 위험 지문은 규칙 ID·파일·정규화한 발췌만 포함해, 질문에 들어가는 지적 문구가 바뀌어도 같다. 결과 캐시 키에 실제 근거·질문·선택지·지원 정보·정책을 포함하고 모델 변경 시 재검토 또는 명시적으로 검증된 재사용 정책을 적용한다. 근거 밖의 보호 장치가 필요한 판단은 불확실로 남기며, 불완전한 응답을 영구 재사용하지 않는다. [위험 지문](../ilsim-runner/src/main/kotlin/com/dochiri/ilsim/runner/risk/RiskReview.kt)
3. **CLI 경량화로 인증·과금·프로젝트 기능을 바꾸지 않는다.** `--bare`는 자동 지침·메모리·확장 기능 로딩을 줄이지만 OAuth와 keychain도 읽지 않는다. 현재 구독 인증 경로에 바로 적용하거나 단발 호출을 API로 바꾸면 기존 인증이 깨지거나 별도 API 비용이 생길 수 있다. 우선 동일 인증에서 도구·입력·중복 실행을 정리하고, 실행 방식 변경은 필요한 컨텍스트와 과금 계약까지 확인한 후 별도로 비교한다. [공식 bare mode 안내](https://code.claude.com/docs/en/headless#start-faster-with-bare-mode)

추가 절감안의 수용 기준은 **동일한 변경에서 작성·검증·검토 횟수가 필요한 만큼만 발생하고, 장애 후에도 산출물·검토 범위·사용자 승인·로그·비용이 보존되는 것**이다. 검증만 실패한 재시도, 세션 부재와 일반 오류, 결과 수신 후 응답 유실, 중지 직후 재배정, 검토 묶음의 부분 실패, 규칙·정책 변경에 대한 캐시 무효화를 각각 확인한다. 모델 판단 품질은 기존 경로와 별도로 비교해야 한다.

## 추가 요구사항: JEV 우선 처리로 AI Agent 사용 최소화

사용자 지시를 반영한 구현 요구사항이다. JEV의 낮은 비용을 적극 활용해, **JEV로 해결 가능한 모든 판단 작업에 우선 적용하고 이후 AI Agent의 호출·도구 사용·입출력 토큰을 최소화한다.** 현재 적용 범위는 위의 적용 현황을 따른다.

### 처리 경로

`정적 처리·유효한 결과 재사용 → JEV 판단으로 완료 가능한지 결정 → JEV로 완료하거나 필요한 부분만 AI Agent로 이관 → 기존 검증·승인`

- 정적 규칙과 유효한 캐시로 해결되는 작업은 그 결과를 사용한다. 남은 작업에서 판단·선별·분류·점수화가 필요한 모든 지점을 JEV 적용 대상으로 관리한다.
- JEV만으로 필요한 결과와 근거를 제공할 수 있고 해당 작업군의 품질 기준이 검증되어 있으면, Agent를 기동하지 않고 결과를 남긴다. 구조화된 판단은 기존 증거·정적 정보·템플릿과 결합해 동일한 산출물·상태·검토 기록 계약을 충족한다.
- 불확실하거나 지원 범위를 벗어난 판단, 새로운 코드·문서·설명 생성, 수정이 필요한 부분은 Agent로 이관한다. JEV가 선별한 관련 근거와 미해결 항목을 전달해 Agent의 재탐색과 중복 판단을 줄인다.
- Agent가 필요한 경우에만 다음 절의 모델·effort 공동 선택을 적용한다. JEV 완료, 결과 재사용, Agent 실행을 포함한 처리 경로 전체에서 기능·품질을 만족하는 예상 총비용 최소화를 목표로 한다.

### 적용 범위

| 영역 | JEV를 우선 적용할 판단 |
|---|---|
| 작업 접수·요구사항 | 작업 종류·난이도·위험·영향 범위 분류, 추가 확인 필요 여부, 기존 산출물·템플릿 재사용 가능성 |
| 컨텍스트 구성 | 관련 코드·문서·테스트·규칙·메모리 후보의 선택과 우선순위, 중복·무관한 근거 판별 |
| 단계 준비·검증 보조 | 요구사항과 TC 후보의 대응, 누락·모순 후보 판정, 변경 범위와 규칙 적용 여부 |
| 위험·규칙 검토 | 정적 후보의 실제 위험·오탐·불확실 분류, 규칙 유지·재검토 후보 평가 |
| 독립 변경 검토 | 근거가 주어진 누락·무관한 변경·테스트 우회·규칙 위반 후보의 판정과 추가 검토 필요 여부 |
| 실행 중 의사결정 | 실패 원인 분류, 재시도 필요 여부, 다음 모델·effort 조합, 추가 도구·컨텍스트 필요 여부 |
| 규칙·메모리 관리 | 중복·충돌·오래된 항목 후보 판정, 승인·재검토 추천, 기존 학습의 적용 가능성 |
| 지속 보정 | 처리 경로와 모델·effort 선택의 적절성 평가, 과소·과대 선택 분류, 표본 비교 평가 대상 선택 |

각 지점은 입력 근거, JEV 질문·선택지·점수 기준, 완료 조건, 불확실 판정, Agent 이관 조건을 정의한다. 정적 처리·JEV·Agent 중 실제 담당 주체와 판단 근거를 이력에 남기며, 새 판단 기능을 추가할 때도 JEV로 처리 가능한지 확인한다.

### 기능 유지와 지속 검증

- 기존 정적 게이트·테스트·변이 검사·사용자 승인과 독립 검토의 역할·범위를 유지한다. 작성 주체의 자체 판단과 독립 검토를 구분하고, JEV로 동등한 검토 범위와 품질이 검증된 항목부터 담당 주체를 전환한다. 개방형 검토에서 새로운 문제를 찾는 기능은 필요한 Agent 검토를 통해 계속 제공한다.
- Agent 호출 생략은 요구된 산출물·검토 범위·근거 추적이 모두 충족된 단위에 적용한다. 판단이 불확실하거나 근거가 부족하면 이관하고, JEV 장애 시에는 유효한 결과 재사용이나 Agent fallback으로 기능을 이어 간다.
- JEV 완료 판정도 실제 검증 결과·사용자 피드백과 비교하고, 완료 판정의 표본을 독립 검토해 놓친 문제를 확인한다. 정확도·과신·불확실 판정과 이관 기준을 작업군별로 계속 보정하고 품질 저하 시 이전 정책으로 되돌린다.
- JEV 요청은 유효한 결과 재사용과 묶음 질문을 활용한다. 평가·재평가·표본 검증 비용까지 총비용에 포함해, Agent 사용량 감소와 완료 작업당 실제 비용 감소를 함께 확인한다.

### 수용 기준

- 판단 지점별 JEV 적용 여부와 미적용 사유를 확인할 수 있으며, 검증된 JEV 처리 가능 항목이 관성적으로 Agent에 전달되지 않는다.
- JEV 완료 가능한 작업은 Agent 호출 없이 같은 기능·결과 계약을 충족하고, 미해결 부분만 이관되는 경우 Agent에는 관련 근거와 남은 작업이 전달된다.
- JEV 완료율·Agent 이관율·JEV 이후 Agent 호출 수·도구 사용·입출력 토큰·총비용을 작업군·단계별로 측정한다. 이관 뒤 재작업과 추가 검토 비용도 포함한다.
- 기존 경로 대비 호출·토큰·비용 감소를 측정하고, 인수·회귀 통과율과 검토 누락·오탐 기준을 유지하는지 함께 검증한다. JEV의 잘못된 완료 판정, 불확실 판정, 장애 fallback과 정책 롤백도 검증한다.

## 추가 요구사항: 모델·추론 강도 공동 선택과 JEV 지속 보정

사용자 지시를 반영한 구현 요구사항이다. 현재 선택·보정 기능의 적용 범위는 위의 적용 현황을 따른다.

### 선택 목표와 후보

**AI Agent가 필요한 작업에서 기능과 품질을 만족할 수 있는 모델·추론 강도 조합 중 예상 총비용이 가장 낮은 조합을 선택한다.** 모델과 effort를 함께 결정하며, 모델 단가나 effort 이름만으로 비용 순서를 고정하지 않는다.

- Haiku·Sonnet·Opus를 실제 라우팅과 실행 후보에 포함한다. 검증된 단순 작업에는 Haiku와 해당 모델이 지원하는 낮은 effort를 실제 배정할 수 있어야 한다.
- 후보는 모델·버전·실행 환경에서 실제 지원하는 effort로 한정한다. `low`, `medium`, `high` 등 지원 여부를 관리하고, 지원하지 않는 조합은 실행 전에 제외한다.
- AI Agent가 필요한 작성, 변경 검토, 위험 검토, 규칙 검토 각각에서 모델과 effort를 선택한다. 독립 검토의 역할과 검증 범위는 유지하고, 검토 모델을 상수로 고정하는 구조도 선택 정책에 연결한다.
- JEV는 단계, 요구사항, 변경 범위, 관련 코드·테스트·규칙, 위험 요소와 유사 작업 이력을 근거로 후보별 수행 가능성·성공 가능성·불확실성을 평가한다. 실제 조합 선택은 기능·품질 조건과 비용을 적용하는 정책이 담당한다.
- 기능·인수·회귀 기준을 만족할 가능성이 요구 수준 이상인 후보 중 최소 비용 조합을 선택한다. 근거가 부족한 후보는 불확실성을 반영하고, 작업 위험에 맞는 검증된 조합을 사용하면서 보정 자료를 수집한다.

비용 비교 기준은 `JEV 평가 + 작성/검토 실행 + 필요한 재시도·상위 조합 전환`의 예상 합계다. 입력·출력·cache 사용량과 실제 과금 조건을 반영하고, 별도 구독 사용량 지표도 함께 추적한다. 한 번의 호출이 싸더라도 반복 실패로 완료 비용이 커지면 우선하지 않는다. 선택 당시 예상 비용과 근거를 기록해 실제 완료 비용과 비교한다.

### 실행 결과를 통한 영점 조절

1. 매 실행에서 작업 특성, JEV의 후보별 평가, 선택한 모델·effort와 이유, 예상 비용, 실제 모델·effort, 토큰·비용, 재시도·전환 경로와 최종 결과를 기록한다. 결과에는 정적 검사·테스트·변이 검사·독립 검토·사용자 승인 및 이후 확인된 회귀를 연결한다.
2. 예측한 성공 가능성과 실제 성공·실패를 계속 비교한다. JEV의 자기평가만으로 적절성을 판정하지 않고 기존 검증과 사용자 피드백을 근거로 과소·과대 선택을 구분한다. 환경·권한·네트워크·도구 오류는 모델의 수행 능력 부족과 분리한다.
3. 능력 부족이 반복되는 작업군은 수행 가능한 다른 조합의 예상 완료 비용을 비교해 보정한다. 더 높은 effort와 상위 모델 중 비용이 낮은 대안을 선택할 수 있어야 하며, 실패 횟수만으로 Opus에 고정 승격하지 않는다.
4. 과도한 모델·effort 선택은 비슷한 작업의 이력과 제한된 비교 평가로 확인한다. 선택한 조합이 한 번 성공했다는 사실만으로 더 싼 조합도 가능했다고 단정하지 않는다. 품질을 유지한 저비용 조합이 확인되면 이후 유사 작업의 선택에 반영한다.
5. 보정은 실행 결과마다 자료를 갱신하고, 작업군별 충분한 표본과 최근 결과를 바탕으로 적용한다. 표본 기준·평가 주기·비교 평가 비용을 설정할 수 있게 하고, 모든 작업을 여러 모델로 중복 실행하지 않도록 표본 평가를 제한한다.
6. 보정 정책·평가 기준·모델 버전을 기록하고 품질이 악화되면 이전 정책으로 되돌릴 수 있게 한다. 이력과 보정값은 서버의 영속 저장소에서 관리해 재시작·다른 PC에서도 이어 사용한다.

평가·검토 결과 재사용은 요구사항, 관련 코드·테스트·규칙, 모델·effort 지원 정보, 평가 기준과 보정 정책 버전이 유효할 때만 적용한다. 요구사항 대화로 작업 범위가 바뀌면 기존 난이도 평가를 그대로 재사용하지 않는다. JEV 장애 시에는 최근 유효한 보정 정책과 작업 위험에 맞는 검증된 조합으로 계속 처리하고, 선택 근거에 fallback을 남긴다.

### 수용 기준

- 검증된 단순 작업이 Haiku와 지원되는 낮은 effort로 실제 배정되고, 선택한 모델·effort가 실행 명령과 결과 이력에 일치한다.
- 수행 가능한 여러 조합이 있으면 재시도·검토까지 포함한 예상 총비용이 가장 낮은 조합을 선택한다. 고가 모델의 낮은 effort가 저가 모델의 높은 effort보다 유리한 경우도 같은 기준으로 비교한다.
- JEV의 과소·과대 선택이 실제 검증 결과와 비교 평가로 확인되면 이후 유사 작업의 선택이 보정되고, 변경 이유와 정책 버전을 확인할 수 있다.
- 비용·통계는 모델 × effort × 작업군·단계별로 성공률, 완료 비용, 재시도·전환, 검토 누락·오탐을 비교할 수 있다. 평가와 보정 자체의 비용도 포함한다.
- 환경 오류가 모델 능력 부족으로 잘못 학습되지 않으며, 미지원 조합·요구사항 변경·JEV 장애·재시작·정책 롤백을 검증한다.
- 기존 기능·사용자 승인·독립 검토와 인수·회귀 기준을 유지한다. 저비용 조합 적용 전후의 품질 비교를 통과해야 하며, 비용 감소만으로 보정 정책을 채택하지 않는다.

## 최초 분석의 검증 기록

아래는 추가 요구사항을 구현하기 전, 현재 동작을 분석한 검증 기록이다.

- 관련 기존 테스트: 16개 클래스, 97건 통과. 모델 선택·비용 합산·실패 경로·검토·JEV 선별·문서 선택·규칙 전달을 확인했다.
- Gradle Wrapper 실행은 sandbox의 파일 잠금용 소켓 생성 권한 제한으로 빌드 시작 전에 실패했다. 대신 기존 컴파일 산출물과 로컬 의존성을 사용해 JUnit Launcher로 실행했다. 이번 검증에서 재컴파일하지 않았다.
- 별도 재현: Sonnet 최소 등급의 두 번째 시도에서 Opus 선택, 검토 모델에 따른 가짜 승격 집계, 동일 세션 누적 비용 중복 합산, 앞선 테스트의 길이로 인한 뒤쪽 관련 테스트 누락, diff 뒷부분 누락을 확인했다.
- 실제 유료 AI 호출·운영 청구 대조·모델 간 품질 비교는 수행하지 않았다. 서비스 코드와 설정은 변경하지 않았다.

## 추가 점검의 검증 기록

- 관련 기존 테스트 9개 클래스, 67건 중 66건 통과. 프로세스 중지 1건은 sandbox가 `ProcessHandle.descendants()`의 sysctl 접근을 거부해 실패했다. 이 환경에서 중지 기능의 통과를 확인하지 못했다.
- Gradle Wrapper는 파일 잠금용 소켓 생성 권한으로 빌드 시작 전에 실패했다. 기존 컴파일 산출물과 로컬 의존성을 JUnit Launcher로 실행했다. 서비스·기존 테스트 소스는 재컴파일하지 않았으며, 임시 재현 코드만 로컬 Kotlin compiler로 컴파일했다.
- 별도 재현: 일반적인 세션 재개 오류 후 Agent 2회 실행, 코드가 같고 검증 명령의 결과만 바뀐 재시도에서도 작성 2회 실행, 위험 검토 두 번째 묶음 실패 시 첫 묶음 결과 미반환, 빈 검토 응답의 PASS·완료 캐시 처리, reviewer 변경 후 규칙 검토 재사용, 지적 문구 변경 후 동일 위험 지문을 확인했다.
- Claude Code `2.1.302`의 옵션과 공식 CLI·구조화 출력·prompt caching 문서를 대조했다. 서비스 코드·설정은 변경하지 않았고, 실제 유료 AI 실행·운영 절감률·모델 품질 동등성은 검증하지 않았다.
